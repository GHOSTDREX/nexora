The journey

Not a green-field build — AgriNova grew out of two existing Python prototypes, then had to survive contact with real hardware and a pre-launch audit.

1
Starting point

Two disconnected prototypes, no app around them

An Irrigation Recommendation FastAPI microservice with a trained Decision Tree pipeline and a rule-based chatbot, plus a separate rule-based Crop Suitability checker and an unused 2,200-row crop dataset. Neither had a database, auth, a dashboard, or a way to reach hardware.

2
Foundation

Built the actual multi-tenant app

FastAPI + SQLAlchemy + SQLite backend with JWT auth and per-farm data isolation, a React + Vite frontend, and a background simulator that writes sensor readings through the same ingestion path a real ESP32 would use — so hardware could be swapped in later without touching the frontend.

3
Going physical

Wired up three real ESP32 boards

A sensor node (DHT22, soil moisture, rain, RS485 NPK), a motor/actuator controller (drive motors, pump, plow, seed dispenser, camera pan), and an AI-Thinker ESP32-CAM streaming MJPEG — all reachable from the backend over plain HTTP on the local WiFi.

4
Real pivots

Cut and swapped features once hardware existed

Rainwater harvesting was dropped entirely once it was clear it didn't fit the build. Fertilizer-dispense was swapped for a plow control once the actual mechanism existed on the rover. A reported "speed slider does nothing" bug traced back to firmware only updating a variable on a speed-only command instead of re-driving the motors — fixed at the source, not papered over in the UI.

5
Pre-hackathon audit

A full security & correctness pass, self-tested with Playwright

Found and fixed a live database bug — a dropped column had left a stale NOT NULL constraint that would have 500'd every new signup at demo time — caught by the test suite itself, not by manual clicking. WiFi credentials were pulled out of committed firmware into gitignored secrets.h files. A 16-test Playwright suite now covers auth, every page, robot controls, language switching, and form validation.

6
Final mile

Made it reachable from a phone, for real

Getting the dashboard onto a phone on the same WiFi surfaced a chain of environment issues, not code bugs: a Windows Firewall rule scoped to the wrong network profile, a stale .env file silently overriding the LAN-aware API URL back to 127.0.0.1, and the backend running on the wrong Python interpreter with a mismatched numpy that broke every ML endpoint. All three had to be found and fixed before demo day, not during it.

7
Hardening pass

A second, deeper security pass against a standard checklist

Account lockout after 5 failed logins, timing-safe login checks so response speed can't reveal which emails are registered, structured security-event logging, HSTS, a 2MB request body cap, CORS narrowed from a wildcard to the exact methods and headers the app actually uses, and explicit anti-prompt-injection instructions wrapping the farm-context data sent to the AI Assistant. Just as deliberately, CSRF tokens and secure cookie flags were left out — the app authenticates with a bearer JWT, not cookies, so those protections don't apply here and would have been theater.

8
Last bug, day-of

The D-pad was driving the rover in the wrong direction — literally rotated

Forward drove right, right drove back, back drove left, left drove forward: a clean four-way rotation, which was the tell that it wasn't a wiring fault but a labeling bug — the four motor patterns in firmware were internally consistent, just assigned to the wrong command names in applyDirection(). Re-mapped in software, no rewiring needed.

Problem & use case

What's broken today

Small and marginal Indian farmers mostly irrigate and fertilize reactively — by eye and habit, not by measurement. Advisory tools that exist are single-language (usually English), assume constant connectivity, and stop at giving advice: nothing actually turns the pump or the plow.

What AgriNova replaces it with

Live soil/NPK/weather readings feed five trained models that answer four concrete questions — irrigate now?, which crop?, which fertilizer?, what yield to expect? — and a physical rover carries out the resulting action, in the farmer's own language.

Architecture

Three tiers: a React dashboard, a FastAPI backend that owns auth and the ML models, and three ESP32 boards on the farm's own WiFi. The backend never lets the browser talk to hardware directly — every hardware call is relayed and SSRF-checked server-side.

Frontend

React 19 + Vite + TypeScript, Tailwind v4, Framer Motion. Dark-mode-first design system, 10 fully translated languages, a raw WebSocket hook for live pushes.

Backend

FastAPI + SQLAlchemy 2.0 + SQLite. JWT auth, one farm per user, every query scoped to farm_id. 13 routers, 5 ML models, a WebSocket connection manager keyed by farm.

Hardware

3 ESP32 boards on the farm's WiFi, addressed by mDNS hostname. No auth on the boards themselves — the backend's SSRF guard is the only gate, blocking loopback / link-local / multicast targets.

AgriRover — the physical robot

A single ESP32-S3 controller drives locomotion and every field actuator, all exposed as one plain-HTTP command surface the backend calls directly.

SubsystemHardwareBehaviourCommand
Drive 2× BTS7960 motor driver, differential (skid-steer) pair PWM speed 0–255, direction re-applies live on a speed-only change move_forward / back / left / right / stop, set_speed&val=
Irrigation pump L298N module #1, channel A Latching relay drive — stays on until told off pump_on / pump_off
Plow L298N module #1, channel B Bang-bang actuator, fixed 100ms raise/lower stroke plow_on / plow_off
Camera pan L298N module #2, channel A · BO gear motor Stepper-style pulses, ±8 steps from center camera_left / right / center
Seed dispenser L298N module #2, channel B · BO gear motor Continuous back-and-forth sweep while active, auto-recenters on stop seed_on / seed_off
Vision Separate ESP32‑CAM (AI-Thinker, OV2640) 320×240 MJPEG stream; backend also samples a single JPEG frame per request GET /stream
Note on the name: the firmware and backend refer to this board simply as ESP32_ROBOT_01 / "the robot controller" — AgriRover is the pitch name for the same physical unit.

AI Assistant — Claude, live

Every chat message is grounded with the farm's live sensor reading, latest prediction, weather, and recent alerts, then answered by the Claude API in whichever of the 10 languages the user has selected.

Fallback Assistant — offline mode

If no API key is configured (or the call fails), a 15-topic rule-based responder answers instead — irrigation, fertilizer, pests, weeds, sowing, harvest, organics — in English, Hindi, or Marathi. The app never breaks for lack of a key.

Security

A checklist-driven hardening pass run against the live app before the hackathon — each item verified working, not just written.

MeasureImplementation
Account lockout5 failed logins locks the account for 15 minutes, tracked per-user in the database
User enumeration preventionLogin runs a bcrypt check against a dummy hash even for unregistered emails, so response timing can't reveal which accounts exist
Security event loggingLogin, registration, and lockout events logged by user id — never raw email or password
Prompt-injection defenseFarm context sent to the AI Assistant is wrapped in explicit data-not-instructions tags; the model is told to decline attempts to override its role
Request size limit2MB cap on every request body, rejected with 413 before it reaches a route handler
Input length boundsChat messages capped at 2,000 characters; all auth fields already bounded by schema
CORS locked downNarrowed from a wildcard to exactly the methods and headers the app uses (GET/POST/PUT/PATCH, Authorization, Content-Type)
HSTSStrict-Transport-Security sent on every response, ready for the moment this sits behind HTTPS
SSRF-guarded hardware relayFarm-configured hardware hostnames are re-resolved and checked against loopback/link-local/multicast before every outbound call
Deliberately not added: CSRF tokens, secure cookie flags, expiring reset links, upload-type whitelisting, directory-listing/admin-route removal. The app authenticates with a bearer JWT (not cookies), so CSRF and cookie flags don't apply; there's no password-reset or file-upload feature yet to harden, and no static directory or admin panel is served. Adding protections for features that don't exist would be security theater, not hardening.

Why it's better

Actually multilingual

10 fully-translated Indian languages across the whole UI, not just a landing page — rare in agri-tech tooling, which is almost always English-only.

Real hardware, not a mockup

Every "robot" button is a live HTTP call to a physical ESP32 driving real motors, not a simulated animation.

Degrades gracefully

No hardware yet? The simulator writes through the same code path. No API key? The chatbot still answers. Nothing hard-fails for lack of a resource.

Real multi-tenancy

Every table is scoped to farm_id, one farm per user, a WebSocket room per farm — not a single shared demo account.

Defense in depth

SSRF-guarded hardware relay, per-account lockout after repeated failed logins, timing-safe auth checks, HSTS, and explicit anti-prompt-injection framing around the data fed to the AI Assistant.

Actually tested

A 16-test Playwright suite runs the real registration → dashboard → robot → language-switch path, not just unit tests around the edges.

Use cases

Check soil, NPK, and weather from a phone without walking the field.

Auto mode turns the pump on at 32% soil moisture and off again at 55%, without a person watching a gauge.
